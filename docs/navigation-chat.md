# Career Chef: conversational navigation API

Career Chef answers application questions in words generated by Gemini and returns
approved page links. It runs at `POST /v1/navigation/chat`. The existing website
on port 3000 includes a floating **Ask Chef** chatbox and a dedicated test page at
`http://127.0.0.1:3000/career-chef`. Use Swagger to test the API independently.
See [website and API testing](career-chef-testing.md) for both entry points.

## Local setup

From the repository root, install Python 3.12+ and PostgreSQL 17 (or Docker), then:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -c requirements.lock -e ".[dev]"
.\.venv\Scripts\python.exe -m scripts.local_dev init
```

`init` creates an ignored `.env` with independent random local-only credentials.
It never overwrites an existing file. If `.env` already exists, preserve its
secrets and configure it explicitly using `.env.example`. Local helpers require
`ENVIRONMENT=development`, `AUTH_MODE=local`, `ALLOW_DEV_AUTH=true`, a loopback
database, encryption and audit keys. Never deploy these development identities.

Set `GEMINI_API_KEY` in `.env` to your Google key; do not paste it into chat, a
browser request, or Git. The default `GEMINI_MODEL` is `gemini-3.8-flash`; choose
a text model available to your Google project. Google's current
[model catalog](https://ai.google.dev/gemini-api/docs/models) lists supported models.
`GEMINI_TIMEOUT_SECONDS` defaults to 20 (maximum 30).

If using Docker, start PostgreSQL with `docker compose up -d postgres`.
For an existing native PostgreSQL server, match the database host, port and local
credentials in `.env`. On this Windows workspace, an ignored portable PostgreSQL
17 cluster may have been provisioned in `.local`; `python -m scripts.local_dev start-db`
starts only that recognized local cluster without resets. The helper does not
download or install PostgreSQL on a fresh checkout. Then prepare the databases
without resetting existing data:

```powershell
.\.venv\Scripts\python.exe -m scripts.local_dev prepare --include-test-database
.\.venv\Scripts\python.exe -m scripts.local_dev check
.\.venv\Scripts\python.exe -m scripts.local_dev serve
```

`check` verifies the local database and schema and reports whether a Gemini key
is configured; it does not contact Google or certify that the key works. `serve`
keeps the API running on loopback. Leave that terminal open.

## Send a message in Swagger

1. Open **http://127.0.0.1:8000/docs** (`docs`, not `docx`).
2. In a second terminal, run
   `.\.venv\Scripts\python.exe -m scripts.local_dev token`.
   Copy the printed token into Swagger's **Authorize** dialog. Paste only the token;
   Swagger adds `Bearer`. This fictional identity expires after 30 minutes and has
   no platform roles. Hosted deployments require a real Supabase access token.
3. Expand **POST /v1/navigation/chat**, then **Try it out**.
4. Enter `chef-test-001` in **Idempotency-Key** and this body:

```json
{
  "message": "How do I start finding jobs?",
  "consent_to_gemini": true,
  "history": []
}
```

5. Click **Execute**, then read **Server response → Response body → data.reply**.
   That field is the actual generated answer. `data.links` contains suggested
   destinations. A 200 response confirms the authenticated request was processed;
   it does not mean any profile, application, offer or account state was changed.

For a follow-up, use a new key and optionally include prior user/assistant pairs:

```json
{
  "message": "What should I do after that?",
  "consent_to_gemini": true,
  "history": [
    {"role": "user", "content": "How do I start finding jobs?"},
    {"role": "assistant", "content": "Paste the previous Career Chef answer here."}
  ]
}
```

Use the actual previous reply. History is optional, caller-supplied context; it is
not trusted proof of application state. It must contain completed alternating
user/assistant pairs, up to 10 turns. User messages are at most 2,000 characters;
assistant history entries allow the full 4,000-character reply, with at most
12,000 characters combined. Each request must explicitly consent
to sending both the message and supplied history to Google. Avoid sensitive data.

You can also send a real single-turn message from a second terminal, without
copying a token or choosing an idempotency key:

```powershell
.\.venv\Scripts\python.exe -m scripts.local_dev ask "How do I start finding jobs?" --consent-to-gemini
```

This calls the running local API and prints its actual answer. It requires the
same database/key setup and explicit consent, and never supplies a mock answer.
The command prints its generated operation key; use `--key` with that key to retry
the same message exactly after a network failure.

## Retry and error handling

Reuse an Idempotency-Key only to retry the exact same body and headers. A completed
retry returns the saved response without a second Gemini request. A new message,
history, or changed request needs a new key. Keys are scoped to the authenticated
actor and route; another user's key cannot retrieve the first user's answer.

| Response | Meaning and next step |
|---|---|
| `401 UNAUTHORIZED` / `INVALID_TOKEN` | Authorize with a valid session; regenerate an expired local token. |
| `403 ORIGIN_FORBIDDEN` | Include the exact docs origin in `CORS_ORIGINS`, then restart the API. Both localhost and 127.0.0.1 on port 8000 are included in local defaults. Hosted origins must explicitly use HTTPS. |
| `409 IDEMPOTENCY_CONFLICT` | A different request used this key. Use a new key for the new message. |
| `422 IDEMPOTENCY_KEY_REQUIRED` / `VALIDATION_ERROR` | Supply an 8–128 character key, a nonempty message, literal `true` consent, and valid history. |
| `429 RATE_LIMITED` | Wait for the write-rate window to reset. |
| `503 CHAT_UNAVAILABLE` | Check the server's Gemini key/model/quota and encryption/audit configuration; retry the exact request after resolving availability. Provider failures are sanitized. |
| Database unavailable / `503` or `500` | Run the local diagnostic, start PostgreSQL, apply migrations, and check credentials. Database and Gemini availability are separate. |

Opening `/docs` only verifies that the documentation server is running. It does
not verify PostgreSQL, authentication, or Gemini. Use `check`, then execute the
authenticated chat request to test those boundaries. If you only need to browse
docs before configuring Gemini, start `uvicorn app.main:app --host 127.0.0.1 --port 8000`;
chat requests will remain unavailable until configuration is complete.

## Integration and safety boundaries

Gemini receives the message, any explicitly supplied history, and a public
navigation guide. The integration sends no account records, resumes, tenant data,
bearer tokens or application permissions. User-supplied text may itself contain
private information, so obtain informed consent before sending it. Provider data
retention is governed by the Google project's terms.

The generated reply is advisory plain text, capped at 4,000 characters. Render
it as text, never HTML. The server validates model JSON and constructs at most
three page links from its catalog. It rejects model-generated URLs/HTML in the
reply. Links confer no permissions; destination APIs retain their ACLs. The
assistant has no tools, cannot perform actions or bypass consent, double opt-in,
attention limits, or shadow-mode matching. Generated guidance can be mistaken;
it is not a reliability certification or a confirmed application outcome.

One PostgreSQL transaction covers successful idempotency, audit and outbox writes.
Audit/outbox contain references and consent, not messages/history. The transcript
is not persisted as a conversation. Encrypted idempotency responses contain the
generated answer and follow the existing seven-day retention policy. The request
fingerprint is keyed; it does not persist the plaintext prompt or history.

Gemini calls have a bounded total timeout and 64 KiB decoded response limit. The
transaction holds the existing actor/idempotency locks during a call, serializing
that actor's writes. Failed transactions roll back the existing write-rate bucket.
The provider cannot participate in the database transaction: a provider success
followed by a database failure can cause another provider call on retry. There is
no claim of exactly-once external billing. No live fallback answer is fabricated.

Uses Google's [generateContent REST API](https://ai.google.dev/api/generate-content)
and structured JSON responses. After contract changes, run
`python scripts/export_openapi.py`, then `npm run generate` and
`npm run typecheck` in `packages/api-client`.
